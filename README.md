# CRM Programming School

CRM-система для обробки заявок на курси. Дві ролі — **admin** (керування менеджерами, статистика) та **manager** (робота із заявками).

## Стек

**Backend**: Node.js (≥ 20.19 або ≥ 22.12), Express, TypeScript, MongoDB (Mongoose), JWT (access/refresh), Joi, ExcelJS, Swagger, node-telegram-bot-api, node-cron.
**Frontend**: React, TypeScript, Vite, React Router, React Hook Form, Axios, Recharts.

## Основні можливості

- Управління заявками (orders): список з фільтрами, сортуванням, пагінацією (25/сторінка), картка заявки, коментарі, редагування, статуси, довільні теги (`tags`), експорт відфільтрованого списку в Excel (див. [Список заявок](#список-заявок)).
- Пошук у шапці — введення прізвища клієнта та Enter переносить на список заявок з відповідним фільтром (інші фільтри при цьому скидаються).
- Автоматичний авторозподіл нових заявок між менеджерами — round-robin або за навантаженням (`/admin/settings`); адмін може вручну перепризначити заявку іншому менеджеру з картки заявки.
- Журнал активності по заявці та повний лог по системі (`/admin/history`).
- Причина відмови (`disagree_reason`) при статусі Disagree та звіт по втратах з графіком (`/admin/loss-report`).
- Автоматизація: позначення прострочених заявок (вмикається в `/admin/settings`), нагадування по задачах, автозміна статусу на Agree при повній оплаті.
- Сповіщення в Telegram та у вбудованому центрі сповіщень CRM (нова заявка, зміна статусу, новий коментар, простроченість, нагадування) — прив'язка Telegram-акаунту через бота в профілі користувача.
- Профіль користувача (`/account`): редагування імені/прізвища/email, зміна пароля, завантаження фото профілю.
- Адмін-панель: керування менеджерами, статистика, налаштування авторозподілу та автоматизації.

## Структура репозиторію

```
backend/    — API сервер
backend/uploads/avatars — завантажені фото профілю (створюється автоматично при старті, у git не потрапляє)
frontend/   — клієнтський застосунок
docs/       — Postman-колекція
dump/       — дамп колекції orders для MongoDB
docker-compose.yml — піднімає mongo + backend + frontend одразу (див. розділ Docker)
```

## Передумови

- Node.js ≥ 20.19 (або ≥ 22.12) — цього вимагають Mongoose 9 / драйвер MongoDB 7 на бекенді та Vite 8 на фронтенді
- Доступ до MongoDB (рекомендовано MongoDB Atlas — потрібен connection string)

## Запуск backend

1. Перейти в директорію бекенду:
   ```
   cd backend
   npm install
   ```

2. Створити файл `.env` на основі `.env.example` і заповнити значення:
   ```
   PORT=5000
   MONGODB_URI=<connection string вашого MongoDB Atlas кластера>
   JWT_ACCESS_SECRET=<довільний секретний рядок>
   JWT_REFRESH_SECRET=<довільний секретний рядок>
   JWT_ACCESS_LIFETIME=10m
   JWT_REFRESH_LIFETIME=20m
   JWT_ACTIVATE_SECRET=<довільний секретний рядок>
   JWT_ACTIVATE_LIFETIME=30m
   ADMIN_EMAIL=admin@gmail.com
   ADMIN_PASSWORD=admin
   TELEGRAM_BOT_TOKEN=<токен бота від @BotFather, опційно>
   ```
   Обов'язкові лише три секрети — `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `JWT_ACTIVATE_SECRET`: без них сервер стартує, але логін і генерація лінків активації падають з помилкою 500. Решта змінних мають значення за замовчуванням (`backend/src/config/config.ts`): `PORT=5000`, `MONGODB_URI=mongodb://localhost:27017/crm`, `JWT_ACCESS_LIFETIME=10m`, `JWT_REFRESH_LIFETIME=20m`, `JWT_ACTIVATE_LIFETIME=30m`, `ADMIN_EMAIL=admin@gmail.com`, `ADMIN_PASSWORD=admin`.
   Якщо `TELEGRAM_BOT_TOKEN` не заданий — Telegram-сповіщення просто вимкнені, решта функціоналу (включно зі сповіщеннями в самій CRM) працює без змін (див. розділ [Сповіщення в CRM та Telegram](#сповіщення-в-crm-та-telegram)).

3. (Опційно) Наповнити базу тестовими заявками з дампу:
   ```
   npm run seed:orders
   ```
   Скрипт читає `dump/orders.dump` (500 заявок без статусу й без менеджера) і вставляє записи у колекцію `orders` бази з `MONGODB_URI` (`backend/.env`). Повторний запуск не створює дублікатів: якщо в базі вже є заявки з email, вставляються лише записи з email, якого в базі ще немає (записи без email у цьому випадку пропускаються).

4. Запустити сервер у режимі розробки:
   ```
   npm run dev
   ```
   Або зібрати й запустити прод-версію:
   ```
   npm run build
   npm start
   ```

Сервер піднімається на `http://localhost:5000` (значення `PORT`). При старті:

- автоматично створюється дефолтний admin (`ADMIN_EMAIL` / `ADMIN_PASSWORD` з `.env`), якщо в базі ще немає користувача з таким email. Пізніша зміна `ADMIN_PASSWORD` у `.env` пароль уже створеного адміна не змінює;
- створюється папка `uploads/avatars` для фото профілю (відносно директорії, з якої запущено сервер, зазвичай `backend/`);
- запускаються фонові задачі (перевірка простроченості кожні 15 хв, нагадування по задачах щохвилини).

## Запуск frontend

1. Перейти в директорію фронтенду:
   ```
   cd frontend
   npm install
   ```

2. Перевірити файл `.env` (у репозиторії він уже є і налаштований на проксі до бекенду):
   ```
   VITE_API_URL=/api
   VITE_TELEGRAM_BOT_USERNAME=<username бота без @, опційно>
   ```
   Якщо створюєте `.env` з `frontend/.env.example`, обов'язково вкажіть `VITE_API_URL=/api` — у прикладі значення порожнє, і тоді запити не потрапляють у проксі до бекенду.
   `VITE_TELEGRAM_BOT_USERNAME` потрібен для кнопки "Open bot" у профілі — без нього кнопка все одно показується, але веде на неробоче посилання; прив'язку Telegram тоді можна виконати вручну кодом (див. нижче).

3. Запустити застосунок:
   ```
   npm run dev
   ```

Фронтенд піднімається на `http://localhost:3000` і проксіює запити `/api/*` (префікс `/api` відкидається) та `/uploads/*` на бекенд (`http://localhost:5000`), маршрутизація прописана в `vite.config.ts`.

## npm-скрипти

Backend (`backend/`, усі скрипти бази працюють з `MONGODB_URI` з `backend/.env`):

| Команда | Що робить |
|---|---|
| `npm run dev` | компілює TypeScript у `dist/` у watch-режимі (tsc-watch) і перезапускає `node dist/app.js` після кожної успішної збірки |
| `npm run build` / `npm start` | збірка в `dist/` / запуск зібраної версії |
| `npm run seed:orders` | імпорт заявок з `dump/orders.dump` (див. вище) |
| `npm run migrate:status-typo` | одноразова міграція старих даних: перейменовує статуси `Aggre` → `Agree` і `Disaggre` → `Disagree` у заявках та в журналі змін; повторний запуск безпечний |
| `npm run migrate:manager-ref` | одноразова міграція старих даних: замінює менеджера, збереженого в заявці рядком-прізвищем, на посилання на користувача з таким прізвищем; невідомі прізвища пропускаються з попередженням у лозі |

Frontend (`frontend/`):

| Команда | Що робить |
|---|---|
| `npm run dev` | dev-сервер Vite на `http://localhost:3000` з проксі до бекенду |
| `npm run build` | перевірка типів (`tsc -b`) і збірка в `frontend/dist/` |
| `npm run preview` | локальний перегляд зібраної версії |
| `npm run lint` | ESLint |

## Запуск через Docker

Альтернатива ручному запуску backend/frontend — весь стек (MongoDB + backend + frontend) одразу:

```
docker compose up --build -d
```

Піднімає три контейнери:

- **mongo** — локальна MongoDB 7 у контейнері (дані зберігаються у volume `mongo_data`, доступ лише всередині docker-мережі, без зовнішнього порту).
- **backend** — збирається з `backend/Dockerfile`, доступний на `http://localhost:5000`. Використовує `backend/.env`, але `MONGODB_URI` примусово перевизначено на локальний `mongo` контейнер (`mongodb://mongo:27017/crm`), а не на Atlas з `.env`. `PORT` у `backend/.env` має залишатися `5000` — `docker-compose.yml` пробрасує саме порт `5000:5000`.
- **frontend** — збирається з `frontend/Dockerfile` (білд + nginx), доступний на `http://localhost:3000`. `nginx.conf` у цій збірці проксіює `/api/*` та `/uploads/*` на прод-бекенд AWS (`crm-aws.eu-north-1.elasticbeanstalk.com`), а не на локальний `backend`-контейнер цього ж `docker-compose.yml` — це навмисна конфігурація прод-збірки. Для локальної перевірки повного стеку через Docker (фронтенд ↔ локальний бекенд) потрібно тимчасово змінити `proxy_pass` у `frontend/nginx.conf` на `http://backend:5000`.

Особливості:

- База в контейнері `mongo` стартує порожньою (бекенд створює в ній лише дефолтного admin). `npm run seed:orders` і `migrate:*` у контейнері бекенду не запустити (у прод-образі немає `tsx` і вихідних `.ts`), а з хоста вони підключаються до `MONGODB_URI` з `backend/.env`. Щоб наповнити контейнерну базу, тимчасово додайте сервісу `mongo` у `docker-compose.yml` `ports: ["27017:27017"]` і з `backend/` виконайте `MONGODB_URI=mongodb://localhost:27017/crm npm run seed:orders`.
- Volume для `uploads` немає: фото профілю зберігаються у файловій системі контейнера `backend` і зникають, коли контейнер перестворюється (`docker compose down`, `docker compose up --build` після змін коду).

Корисні команди:

```
docker compose ps                # статус контейнерів
docker compose logs -f backend   # логи одного сервісу
docker compose stop              # зупинити, зберігши контейнери й дані
docker compose down              # зупинити і прибрати контейнери (volume з даними Mongo залишається)
docker compose down -v           # + видалити дані Mongo з volume
```

Це production-подібна збірка без live-reload — після зміни коду для оновлення контейнерів потрібно повторити `docker compose up --build -d`. Для розробки з гарячим перезавантаженням використовуйте ручний запуск (`npm run dev`) з розділів вище.

## Вхід у систему

При переході на хост відкривається сторінка логінації. Дефолтний адміністратор:

- **Email**: `admin@gmail.com`
- **Password**: `admin`

Менеджерів створює адмін через адмін-панель (`/admin`) — після створення потрібно активувати акаунт (кнопка ACTIVATE генерує одноразовий лінк активації з обмеженим часом дії) і встановити пароль за цим лінком (див. [Керування менеджерами](#керування-менеджерами)).

Відповіді `POST /auth/login`:

- `200` — `{ user, tokens: { accessToken, refreshToken } }` (без поля `password`).
- `400` — у тілі немає `email` або `password` (або це не рядки).
- `401 Invalid email or password` — невірний email чи пароль, а також акаунт, для якого ще не встановлено пароль (неактивований менеджер). Пароль перевіряється першим, тож з невірним паролем не можна дізнатися, чи акаунт забанений.
- `403 User is banned` / `403 User is not activate` — пароль правильний, але акаунт забанений або неактивний.
- `429` — більше 10 спроб входу за 15 хвилин з одного IP.

Access-токен живе `JWT_ACCESS_LIFETIME` (за замовчуванням 10 хв), refresh — `JWT_REFRESH_LIFETIME` (20 хв). Фронтенд на відповідь `401` один раз оновлює токени через `POST /auth/refresh` і повторює запит; якщо оновити не вдалося — перекидає на сторінку логіну.

## Керування менеджерами

Адмін-панель (`/admin`) показує загальну статистику заявок і картки всіх користувачів (включно з адмінами), по 25 на сторінку.

- **Створення** — кнопка "+ Create manager": email (унікальний), ім'я та прізвище. Ім'я і прізвище мають починатися з великої літери й містити лише літери (латиниця або кирилиця), апостроф чи дефіс, 2–50 символів (`Ol'ha`, `Anna-Maria`). Ті самі правила діють при редагуванні профілю.
- **Активація** — кнопка ACTIVATE на картці неактивного користувача генерує лінк `<адреса фронтенду>/activate/<token>` і копіює його в буфер обміну (якщо скопіювати не вдалося — лінк показується у сповіщенні). Лінк діє `JWT_ACTIVATE_LIFETIME` (за замовчуванням 30 хв) і спрацьовує один раз. За ним менеджер задає пароль (8–128 символів), після чого акаунт стає активним. Доки пароль не встановлено, логін повертає `401`.
- **Відновлення пароля** — для активних користувачів замість ACTIVATE показується RECOVERY PASSWORD: генерує такий самий одноразовий лінк `/activate/<token>`. Після встановлення нового пароля всі сесії користувача завершуються.
- **Бан / розбан** — BAN одразу завершує всі сесії користувача; забанений не може увійти (`403`) і не отримує нових заявок з авторозподілу. Забанити самого себе не можна.
- **Статистика на картках** — кількість заявок користувача всього і по кожному статусу (статуси без заявок показуються як 0). Картки поточної сторінки завантажуються одним запитом `GET /users/statistic?ids=id1,id2,…` (лише admin, до 100 id через кому; відповідь — об'єкт `id → { total, <статус>: кількість }`, статуси без заявок у відповіді відсутні). `GET /users/:id/statistic` доступний адміну для будь-якого користувача, а менеджеру — лише для власного id (інакше `403`).
- **Видалення** — лише через API, кнопки в UI немає: `DELETE /users/:id` (тільки admin). Видалити себе чи будь-якого адміна не можна (`403`), неіснуючий id — `404`. При видаленні:
  - усі токени користувача відкликаються (сесії завершуються);
  - його заявки в статусі `In work` повертаються в `New` (`status_updated_at` — поточний час, `is_overdue: false`), а з усіх його заявок знімається менеджер (`manager: null`) — вони знову вільні;
  - видаляються його невиконані задачі, сповіщення та коди прив'язки Telegram;
  - він прибирається з учасників авторозподілу;
  - сам користувач видаляється з бази остаточно.

## Статуси заявок

`New`, `In work`, `Agree`, `Disagree`, `Dubbing`.

- Нова заявка (`POST /orders`) завжди отримує статус `New`.
- Заявка без статусу (`null` — так імпортуються всі заявки з дампу, або порожній статус, збережений через редагування) вважається `New`: фільтр `status=New` її знаходить, у статистиці вона рахується як `New`.
- Перше редагування або коментар заявки зі статусом `New`/без статусу переводить її в `In work` (див. [Авторозподіл заявок](#авторозподіл-заявок)).
- Для `Disagree` обов'язкова причина відмови `disagree_reason` (до 200 символів) і опційний коментар `disagree_reason_comment` (до 1000). В UI причину обирають зі списку (High price, Chose another school, Not answering calls, Changed mind, Other) або вводять свою. При переході в будь-який інший статус причина очищується.

## Список заявок

Сторінка `/orders`:

- **Фільтри**: ім'я, прізвище, email, телефон, група — пошук підрядка без урахування регістру (спецсимволи на кшталт `+`, `(`, `.` шукаються буквально); курс, формат, тип, статус і вік — точний збіг; період — за датою створення заявки, кінцева дата включає весь день; "My orders" — лише заявки поточного користувача. Фільтри застосовуються через ~0,5 с після введення.
- Фільтри, сортування і сторінка зберігаються в URL (наприклад, `/orders?status=New&page=2&order=-created_at`) — посиланням можна поділитися, а кнопка "Назад" у браузері повертає попередні фільтри. За замовчуванням новіші заявки зверху. Пошук у шапці відкриває `/orders?surname=<прізвище>` зі скинутими іншими фільтрами.
- При зміні фільтрів попередній незавершений запит скасовується; **Refresh** перезавантажує поточну сторінку з тими ж фільтрами.
- **Excel** завантажує `orders.xlsx` з усіма заявками, що відповідають поточним фільтрам і сортуванню (без пагінації). Колонки: ID, Name, Surname, Email, Phone, Age, Course, Course format, Course type, Status, Sum, Already paid, Created at, Manager, Group. На експорт фронтенд чекає до 60 с (на звичайні запити — 5 с).

## Адмінські розділи

Доступні з адмін-панелі (`/admin`) кнопками поруч з "+ Create manager":

- **Activity Log** (`/admin/history`) — журнал усіх подій по замовленнях (зміна статусу/менеджера/групи, редагування полів, коментарі) з фільтром по користувачу та даті (кінцева дата включає весь день).
- **Loss Report** (`/admin/loss-report`) — розбивка відмов (`status: Disagree`) по причині (`disagree_reason`) за обраний період (за датою переходу в `Disagree`), у вигляді барчарту (Recharts) і таблиці з відсотками.
- **Settings** (`/admin/settings`) — налаштування авторозподілу заявок (увімкнути/вимкнути, режим round-robin/за навантаженням, менеджери-учасники) та налаштування простроченості заявок (увімкнути/вимкнути, порогове значення годин). Після першого запуску обидві функції вимкнені.

Кожна заявка має історію змін під коментарями у розгорнутій картці, а зміна статусу на `Disagree` (через форму Edit або зі стрічки коментаря) вимагає вказати причину відмови. У тій же картці можна створити задачу-нагадування (з датою) на себе — якщо статус заявки не зміниться до настання дедлайну, прийде сповіщення.

## Автоматизація та тригери

- **Прострочені заявки** — працює, лише якщо перевірку увімкнено в `/admin/settings` (за замовчуванням вимкнено). Кожні 15 хв фоновий процес перевіряє замовлення в статусі `New` (порожній/відсутній статус теж рахується як `New`), що не мають жодного коментаря і перебувають у цьому статусі довше порогу з `/admin/settings` (`thresholdHours`, за замовчуванням 24 год, відлік від часу останньої зміни статусу, а за її відсутності — від дати створення заявки). Такі заявки позначаються `is_overdue: true`, і менеджеру/адмінам надсилається сповіщення. Позначка знімається при зміні статусу або будь-якому коментарі.
- **Нагадування по задачах** — кожну хвилину перевіряються задачі (`Task`) з `dueDate` в минулому, які ще не позначені виконаними. Якщо статус заявки не змінився з моменту створення задачі — виконавцю один раз надсилається нагадування: завжди в центр сповіщень CRM і в Telegram, якщо там увімкнено подію «нагадування». Задачу можна створити й на заявку без статусу (вона вважається `New`).
- **Автоматична зміна статусу на Agree** — при редагуванні заявки (`PATCH /orders/:id`), якщо `sum` більше 0, `already_paid` досягає або перевищує `sum`, а статус у запиті не вказано (або передано порожнім), статус автоматично встановлюється в `Agree`.

## Авторозподіл заявок

Нові заявки створюються через `POST /orders` (публічний ендпоінт, без авторизації — призначений для зовнішніх форм/вебхуків). Якщо авторозподіл увімкнено в `/admin/settings` (за замовчуванням вимкнено):

- **round_robin** — заявка йде по черзі наступному активному менеджеру зі списку учасників.
- **load_based** — заявка йде менеджеру з найменшою кількістю активних (`In work`) заявок серед учасників.

Якщо авторозподіл вимкнено, список учасників порожній або серед учасників немає жодного активного менеджера (активований, не забанений) — заявка створюється без менеджера. Будь-який користувач (роль manager або admin) отримує вільну заявку у власність автоматично при першому редагуванні або коментарі (статус `New`/порожній при цьому змінюється на `In work`). Виняток: якщо при редагуванні вільної заявки явно передати статус `New`, вона залишається вільною і в статусі `New`. Зміна тегів власника не призначає. Якщо заявка вже закріплена за іншим користувачем, редагування, коментування та зміна тегів чужої заявки заборонені (`403`) — це правило діє однаково і для admin.

Якщо статус заявки вручну повертають на `New` (через форму редагування), заявка автоматично звільняється — поле `manager` скидається, і вона знову доступна для призначення.

Адмін може в будь-який момент перепризначити заявку іншому менеджеру (`PATCH /orders/:id/reassign`, тільки роль admin), незалежно від поточного власника. Новим власником може бути лише користувач з роллю manager (інакше `400 Manager not found`). Зміна логується в журнал активності, новий менеджер отримує сповіщення (подія «зміна статусу»).

## Профіль користувача

На сторінці `/account` кожен користувач може:

- Редагувати ім'я, прізвище та email (`PUT /users/:id`) — правила для імені/прізвища ті самі, що при створенні менеджера, email має бути унікальним. Менеджер може редагувати лише власний профіль (`403`), адмін — будь-який.
- Змінити пароль, вказавши поточний (`POST /auth/change-password`) — новий пароль 8–128 символів; невірний поточний пароль — `400 Current password is incorrect`. При успіху всі активні токени користувача інвалідуються і потрібно увійти заново. Те саме відбувається при встановленні пароля за лінком активації/відновлення, а бан одразу завершує всі сесії менеджера.
- Завантажити фото профілю (`POST /users/:id/avatar`, multipart-поле `avatar`) — JPEG/PNG/WEBP до 5 МБ. Файл зберігається на диску сервера (`uploads/avatars`) під випадковим іменем з розширенням за типом файлу (`.jpg`/`.png`/`.webp`, а не з імені завантаженого файлу), попереднє фото видаляється. Файли роздаються статично за `/uploads/avatars/*` із заголовком `X-Content-Type-Options: nosniff`. Інший тип, файл понад 5 МБ, інше ім'я поля або відсутність файлу — `400`; спроба менеджера завантажити фото для чужого id — `403` (файл одразу видаляється). У Docker фото не переживають перестворення контейнера (див. [Запуск через Docker](#запуск-через-docker)).

## Сповіщення в CRM та Telegram

Для кожної події (нова заявка, зміна статусу, новий коментар, простроченість заявки, нагадування по задачі) сповіщення надсилаються одразу двома каналами:

- **У самій CRM** — дзвіночок у шапці показує лічильник непрочитаних (оновлюється кожні 30 с) і список останніх сповіщень (`GET /notifications`, `GET /notifications/unread-count`), з можливістю позначити одне або всі як прочитані. Сповіщення в CRM створюються завжди, незалежно від Telegram.
- **У Telegram** — потребує прив'язки акаунту в профілі (`/account`):
  1. Натиснути "Link Telegram" — згенерується одноразовий код, дійсний 10 хвилин.
  2. Перейти за посиланням "Open bot" (або знайти бота вручну за `VITE_TELEGRAM_BOT_USERNAME`) і надіслати команду `/start <код>`. Після відповіді бота про успішну прив'язку — оновити сторінку профілю.
  3. Обрати, про які події сповіщати: нова заявка, зміна статусу, новий коментар, простроченість, нагадування. Після прив'язки всі події вимкнені — доки їх не увімкнути, у Telegram нічого не приходить.

Хто отримує сповіщення (однаково в CRM і в Telegram):

| Подія | Отримувачі |
|---|---|
| Нова заявка | усі адміни; менеджер, якому заявку призначив авторозподіл |
| Зміна статусу (редагування, коментар зі статусом, автозміна на Agree) | менеджер заявки (при зміні через коментар — якщо змінив не він сам); адміни, крім автора зміни |
| Новий коментар | менеджер заявки, якщо коментар залишив не він; адміни, крім автора коментаря |
| Перепризначення заявки адміном | новий менеджер (подія «зміна статусу») |
| Простроченість | менеджер заявки (якщо є); усі адміни |
| Нагадування по задачі | виконавець задачі |

У Telegram повідомлення надсилається, лише якщо в бекенді заданий `TELEGRAM_BOT_TOKEN`, отримувач прив'язав акаунт і увімкнув цю подію. Помилка доставки в Telegram (наприклад, користувач заблокував бота) не ламає основну дію — вона лише пишеться в лог як попередження.

Без `TELEGRAM_BOT_TOKEN` в `.env` бекенду бот не піднімається і Telegram-повідомлення не надсилаються. Telegram-секція профілю при цьому виглядає так само (кнопка "Link Telegram" генерує код, "Open bot" показується), але прив'язка не завершиться — команду `/start` нікому обробити. Сповіщення в самій CRM працюють незалежно від цього.

## Документація API

- Swagger доступний після запуску бекенду за адресою: `http://localhost:5000/docs`
- Postman-колекція: [`docs/CRM.postman_collection.json`](docs/CRM.postman_collection.json) — містить опис флоу автентифікації та приклади запитів по всіх ендпоінтах (auth, users, orders, groups, history, telegram, auto-assign, overdue-settings, tasks, notifications)
- Чутливі ендпоінти (`/auth/login`, `/auth/set-password`, `/auth/change-password`, `/orders` create, `/telegram/link-code`) обмежені rate-limit'ом — не більше 10–20 запитів на 15 хвилин з одного IP (відповідь `429`).

### Обмеження та формати

- Помилки повертаються як `{ "status": <код>, "message": "<текст>" }` (відповідь `429` — лише `{ "message" }`).
- Ендпоінти з тілом запиту валідують його: відсутнє або невалідне тіло — `400` з описом першої помилки (зокрема `POST /auth/login` і `POST /orders` без тіла).
- Ідентифікатори (`:id` у шляху, `author` у `GET /history`, `assignee` задачі, `manager` у reassign, `participantIds`, `ids` у `GET /users/statistic`) мають бути валідними ObjectId (24 hex-символи), інакше `400`.
- `pageSize` у списках (`/orders`, `/orders/excel`, `/users`, `/history`, `/notifications`) — від 1 до 100, більше — `400`. За замовчуванням 25 (`/notifications` — 20). `/orders/excel` пагінацію ігнорує і віддає всі відповідні заявки.
- `start_date` / `end_date` (`/orders`, `/orders/excel`, `/orders/loss-report`, `/history`) — ISO-дата або дата-час. `start_date` — включно від. `end_date` у форматі `YYYY-MM-DD` включає весь день (до наступної півночі UTC), повна дата-час — включно до вказаного моменту. Звіт по втратах фільтрує за датою переходу в `Disagree`, решта — за датою створення.
- `search` у `GET /users` — підрядок в імені або email без урахування регістру; спецсимволи шукаються буквально.
- Сортування списків — параметр `order` з назвою поля, `-` на початку означає спадання (`order=-created_at`).

## Логи

Бекенд пише логи в stdout/stderr через `backend/src/config/logger.ts` у форматі `[2026-10-24T12:00:00.000Z] INFO повідомлення`:

- `ERROR` — усі відповіді 5xx (глобальний обробник помилок логує метод, URL і саму помилку), помилки фонових задач (перевірка простроченості, нагадування), невдале підключення до MongoDB;
- `WARN` — невдала доставка повідомлення в Telegram, пропущені записи в міграціях;
- `INFO` — старт сервера, підключення до MongoDB, створення дефолтного admin, результати seed і міграцій.

Помилки 4xx (валідація, 401/403/404) не логуються. Переглянути логи: у терміналі з `npm run dev` / `npm start` або `docker compose logs -f backend`.
