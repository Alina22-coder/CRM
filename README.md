# CRM Programming School

CRM-система для обробки заявок на курси. Дві ролі — **admin** (керування менеджерами, статистика) та **manager** (робота із заявками).

## Стек

**Backend**: Node.js (18+, рекомендовано 20+), Express, TypeScript, MongoDB (Mongoose), JWT (access/refresh), Joi, ExcelJS, Swagger, node-telegram-bot-api, node-cron.
**Frontend**: React, TypeScript, Vite, React Router, React Hook Form, Axios, Recharts.

## Основні можливості

- Управління заявками (orders): список з фільтрами, сортуванням, пагінацією (25/сторінка), картка заявки, коментарі, редагування, статуси, довільні теги (`tags`).
- Пошук у шапці — введення прізвища клієнта та Enter переносить на список заявок з відповідним фільтром.
- Автоматичний авторозподіл нових заявок між менеджерами — round-robin або за навантаженням (`/admin/settings`); адмін може вручну перепризначити заявку іншому менеджеру з картки заявки.
- Журнал активності по заявці та повний лог по системі (`/admin/history`).
- Причина відмови (`disagree_reason`) при статусі Disagree та звіт по втратах з графіком (`/admin/loss-report`).
- Автоматизація: позначення просрочених заявок, нагадування по задачах, автозміна статусу на Agree при повній оплаті (`/admin/settings`).
- Сповіщення в Telegram та у вбудованому центрі сповіщень CRM (нова заявка, зміна статусу, новий коментар, простроченість, нагадування) — прив'язка Telegram-акаунту через бота в профілі користувача.
- Профіль користувача (`/account`): редагування імені/прізвища/email, зміна пароля, завантаження фото профілю.
- Адмін-панель: керування менеджерами, статистика, налаштування авторозподілу та автоматизації.

## Структура репозиторію

```
backend/    — API сервер
frontend/   — клієнтський застосунок
docs/       — Postman-колекція
dump/       — дамп колекції orders для MongoDB
docker-compose.yml — піднімає mongo + backend + frontend одразу (див. розділ Docker)
```

## Передумови

- Node.js 18+
- Доступ до MongoDB (рекомендовано MongoDB Atlas — потрібен connection string)

## Запуск backend

1. Перейти в директорію бекенду:
   ```
   cd backend
   npm install
   ```

2. Створити файл `.env` на основі `.env.example` і заповнити значення:
   ```
   PORT=5000
   MONGODB_URI=<connection string вашого MongoDB Atlas кластера>
   JWT_ACCESS_SECRET=<довільний секретний рядок>
   JWT_REFRESH_SECRET=<довільний секретний рядок>
   JWT_ACCESS_LIFETIME=10m
   JWT_REFRESH_LIFETIME=20m
   JWT_ACTIVATE_SECRET=<довільний секретний рядок>
   JWT_ACTIVATE_LIFETIME=30m
   ADMIN_EMAIL=admin@gmail.com
   ADMIN_PASSWORD=admin
   TELEGRAM_BOT_TOKEN=<токен бота від @BotFather, опційно>
   ```
   Якщо `TELEGRAM_BOT_TOKEN` не заданий — Telegram-сповіщення просто вимкнені, решта функціоналу (включно зі сповіщеннями в самій CRM) працює без змін (див. розділ [Сповіщення в CRM та Telegram](#сповіщення-в-crm-та-telegram)).

3. (Опційно) Наповнити базу тестовими заявками з дампу:
   ```
   npm run seed:orders
   ```
   Скрипт читає `dump/orders.dump` і вставляє записи у колекцію `orders`.

4. Запустити сервер у режимі розробки:
   ```
   npm run dev
   ```
   Або зібрати й запустити прод-версію:
   ```
   npm run build
   npm start
   ```

Сервер піднімається на `http://localhost:5000`. При старті автоматично створюється дефолтний admin (`ADMIN_EMAIL` / `ADMIN_PASSWORD` з `.env`), якщо його ще немає в базі.

## Запуск frontend

1. Перейти в директорію фронтенду:
   ```
   cd frontend
   npm install
   ```

2. Перевірити файл `.env` (за замовчуванням вже налаштовано на проксі до бекенду):
   ```
   VITE_API_URL=/api
   VITE_TELEGRAM_BOT_USERNAME=<username бота без @, опційно>
   ```
   `VITE_TELEGRAM_BOT_USERNAME` потрібен лише для кнопки "Open bot" у профілі — без нього прив'язку Telegram можна виконати вручну кодом (див. нижче).

3. Запустити застосунок:
   ```
   npm run dev
   ```

Фронтенд піднімається на `http://localhost:3000` і проксіює всі запити `/api/*` на бекенд (`http://localhost:5000`), маршрутизація прописана в `vite.config.ts`.

## Запуск через Docker

Альтернатива ручному запуску backend/frontend — весь стек (MongoDB + backend + frontend) одразу:

```
docker compose up --build -d
```

Піднімає три контейнери:

- **mongo** — локальна MongoDB 7 у контейнері (дані зберігаються у volume `mongo_data`, доступ лише всередині docker-мережі, без зовнішнього порту).
- **backend** — збирається з `backend/Dockerfile`, доступний на `http://localhost:5000`. Використовує `backend/.env`, але `MONGODB_URI` примусово перевизначено на локальний `mongo` контейнер (`mongodb://mongo:27017/crm`), а не на Atlas з `.env`.
- **frontend** — збирається з `frontend/Dockerfile` (білд + nginx), доступний на `http://localhost:3000`. `nginx.conf` у цій збірці проксіює `/api/*` та `/uploads/*` на прод-бекенд AWS (`crm-aws.eu-north-1.elasticbeanstalk.com`), а не на локальний `backend`-контейнер цього ж `docker-compose.yml` — це навмисна конфігурація прод-збірки. Для локальної перевірки повного стеку через Docker (фронтенд ↔ локальний бекенд) потрібно тимчасово змінити `proxy_pass` у `frontend/nginx.conf` на `http://backend:5000`.

Корисні команди:

```
docker compose ps                # статус контейнерів
docker compose logs -f backend   # логи одного сервісу
docker compose stop              # зупинити, зберігши контейнери й дані
docker compose down              # зупинити і прибрати контейнери (volume з даними Mongo залишається)
docker compose down -v           # + видалити дані Mongo з volume
```

Це production-подібна збірка без live-reload — після зміни коду для оновлення контейнерів потрібно повторити `docker compose up --build -d`. Для розробки з гарячим перезавантаженням використовуйте ручний запуск (`npm run dev`) з розділів вище.

## Вхід у систему

При переході на хост відкривається сторінка логінації. Дефолтний адміністратор:

- **Email**: `admin@gmail.com`
- **Password**: `admin`

Менеджерів створює адмін через адмін-панель (`/admin`) — після створення потрібно активувати акаунт (кнопка Activate згенерує лінк активації з обмеженим часом дії) і встановити пароль за цим лінком.

## Адмінські розділи

Доступні з адмін-панелі (`/admin`) кнопками поруч з "+ Create manager":

- **Activity Log** (`/admin/history`) — журнал усіх подій по замовленнях (зміна статусу/менеджера/групи, редагування полів, коментарі) з фільтром по користувачу та даті.
- **Loss Report** (`/admin/loss-report`) — розбивка відмов (`status: Disagree`) по причині (`disagree_reason`) за обраний період, у вигляді барчарту (Recharts) і таблиці з відсотками.
- **Settings** (`/admin/settings`) — налаштування авторозподілу заявок (увімкнути/вимкнути, режим round-robin/за навантаженням, менеджери-учасники) та налаштування простроченості заявок (увімкнути/вимкнути, порогове значення годин).

Кожна заявка має історію змін під коментарями у розгорнутій картці, а зміна статусу на `Disagree` (через форму Edit або зі стрічки коментаря) вимагає вказати причину відмови. У тій же картці можна створити задачу-нагадування (з датою) на себе — якщо статус заявки не зміниться до настання дедлайну, прийде сповіщення.

## Автоматизація та тригери

- **Прострочені заявки** — кожні 15 хв фоновий процес перевіряє замовлення в статусі `New` (порожній/відсутній статус теж рахується як `New`), що не мають жодного коментаря і перебувають у цьому статусі довше порогу з `/admin/settings` (`thresholdHours`, за замовчуванням 24 год, відлік від часу останньої зміни статусу, а за її відсутності — від дати створення заявки). Такі заявки позначаються `is_overdue: true`, і менеджеру/адмінам надсилається сповіщення.
- **Нагадування по задачах** — кожну хвилину перевіряються задачі (`Task`) з `dueDate` в минулому, які ще не позначені виконаними. Якщо статус заявки не змінився з моменту створення задачі — виконавцю надсилається нагадування (в Telegram, за налаштуванням підписки).
- **Автоматична зміна статусу на Agree** — при редагуванні заявки (`PATCH /orders/:id`), якщо `already_paid` досягає або перевищує `sum` і статус не вказано явно в запиті, статус автоматично встановлюється в `Agree`.

## Авторозподіл заявок

Нові заявки створюються через `POST /orders` (публічний ендпоінт, без авторизації — призначений для зовнішніх форм/вебхуків). Якщо авторозподіл увімкнено в `/admin/settings`:

- **round_robin** — заявка йде по черзі наступному активному менеджеру зі списку учасників.
- **load_based** — заявка йде менеджеру з найменшою кількістю активних (`In work`) заявок серед учасників.

Якщо авторозподіл вимкнено або список учасників порожній — заявка створюється без менеджера. Будь-який користувач (роль manager або admin) отримує заявку у власність автоматично при першому редагуванні, коментарі або зміні тегів; якщо заявка вже закріплена за іншим користувачем, редагування, коментування та зміна тегів чужої заявки заборонені — це правило діє однаково і для admin.

Якщо статус заявки вручну повертають на `New` (через форму редагування), заявка автоматично звільняється — поле `manager` скидається, і вона знову доступна для призначення.

Адмін може в будь-який момент перепризначити вже призначену заявку іншому менеджеру (`PATCH /orders/:id/reassign`, тільки роль admin) — зміна логується в журнал активності, новий менеджер отримує сповіщення.

## Профіль користувача

На сторінці `/account` кожен користувач може:

- Редагувати ім'я, прізвище та email (`PUT /users/:id`).
- Змінити пароль, вказавши поточний (`POST /auth/change-password`) — при успіху всі активні токени користувача інвалідуються.
- Завантажити фото профілю (`POST /users/:id/avatar`) — приймає JPEG/PNG/WEBP до 5 МБ, файл зберігається на диску сервера й роздається статично за `/uploads/avatars/*`.

## Сповіщення в CRM та Telegram

Для кожної події (нова заявка, зміна статусу, новий коментар, простроченість заявки, нагадування по задачі) сповіщення надсилаються одразу двома каналами:

- **У самій CRM** — дзвіночок у шапці показує лічильник непрочитаних і список останніх сповіщень (`GET /notifications`, `GET /notifications/unread-count`), з можливістю позначити одне або всі як прочитані.
- **У Telegram** — потребує прив'язки акаунту в профілі (`/account`):
  1. Натиснути "Link Telegram" — згенерується одноразовий код.
  2. Перейти за посиланням "Open bot" (або знайти бота вручну за `VITE_TELEGRAM_BOT_USERNAME`) і надіслати команду `/start <код>`.
  3. Обрати, про які події сповіщати: нова заявка, зміна статусу, новий коментар, простроченість, нагадування.

Без `TELEGRAM_BOT_TOKEN` в `.env` бекенду бот не піднімається — Telegram-секція профілю просто не показує кнопку прив'язки з активним посиланням, а сповіщення в самій CRM продовжують працювати незалежно від цього.

## Документація API

- Swagger доступний після запуску бекенду за адресою: `http://localhost:5000/docs`
- Postman-колекція: [`docs/CRM.postman_collection.json`](docs/CRM.postman_collection.json) — містить опис флоу автентифікації та приклади запитів по всіх ендпоінтах (auth, users, orders, groups, history, telegram, auto-assign, overdue-settings, tasks, notifications)
- Чутливі ендпоінти (`/auth/login`, `/auth/set-password`, `/auth/change-password`, `/orders` create, `/telegram/link-code`) обмежені rate-limit'ом — не більше 10–20 запитів на 15 хвилин з одного IP.
